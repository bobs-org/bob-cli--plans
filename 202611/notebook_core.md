## 1. Recognition and a reusable snapshot

Add and re-export `frontmatter_is_notebook` beside the existing predicates. Reserve
`notebook` in `records/schema.rs::RESERVED_RECORD_IDS` and document that reservation in
`docs/records.md`.

Add `src/native/notebooks/{mod,model,scan,rules,cli,output}.rs`, with tests split out as
appropriate. Expose a crate-local scan result reusable by the later catalog and capture
phases; keep serialization and terminal output separate from scanning and validation.

Perform one sorted recursive discovery pass over Markdown files, using
`is_excluded_directory` plus `_templates/` (the existing helper already excludes
`done/`). Index relative paths once. Read frontmatter for every included note, including
refs and configured record types, because child-kind validation needs them. Read and
retain full bodies only for notebooks. A buffered header reader can continue through the
body when it discovers a notebook. Do not rescan the vault once per notebook or read
every non-notebook body just for ownership.

Build one indexed `HomeSource` from these header buffers/facts and the shared
`NoteIndex`, then use `HomeResolver::resolve_note` for ownership, root, and hue. Use
`Home.key` as the owner and `Home.root_parent` as the root; retain canonical relative
paths internally and serialize route/stem identifiers in the public fields. Do not
introduce `NoteKind::Notebook` or duplicate the root-selection algorithm. A cached-facts
`HomeSource` adapter is appropriate if it avoids unnecessary parsing or changes to the
Stats source.

Parse notebook parent edges using `wikilink_path_target` and the shared index. Accept
quoted `"[[dev]]"`, bare `[[dev]]`, and `[[dev.md|label]]`, including path-qualified
links. Check that there is exactly one parent target; do not silently pick one of
duplicate keys or a multi-parent value. A direct parent may be an area, a project of any
status, or a notebook. Distinguish absent/unresolved parents, ambiguity, and disallowed
kinds. Validate the parent graph for cycles and invalid chains with memoized traversal
and visited paths; this is validation, not another implementation of ownership. Invalid
notebooks remain visible in reports with findings and without a fabricated owner/root or
recursive loop.

Derive each notebook's title from the first H1 before its first bullet or H2, reducing
wikilinks to their display text and stripping emphasis; otherwise use the first
`aliases` entry, then the existing `humanize_stem` helper. Reuse or expose that helper
without copying its implementation. Keep the file stem as identity. Collect direct child
notebooks, root-to-notebook display breadcrumbs, total top-level note-bullet count, H2
titles with their note counts, and the latest valid `[created::]` date anywhere in the
file, or null, as specified by the parent contract. Nested detail does not increment
note counts. Ignore fenced examples when deriving body structure; never use file mtimes
as recency.

Keep ordering deterministic: roots and siblings by display title case-insensitively,
with a path tie-breaker. Keep the full scan model available to later phases rather than
restricting it to the currently rendered root.

## 2. Findings and Markdown rules

Findings carry a stable code, `error` or `warning` severity, a 1-based source line where
applicable, and a useful message. Report every applicable finding, not just the first.
Include the offending child's path/line in child-kind messages so an
area/project/ref/record with a bad parent can be located from the notebook's findings.
Load record-type configuration once for classification; do not confuse record collection
notes with record instances.

Implement the parent plan's exact codes and severities:

| Code                          | Severity | Trigger                                                                               |
| ----------------------------- | -------- | ------------------------------------------------------------------------------------- |
| `notebook_parent_missing`     | error    | Missing/empty/unresolvable single parent                                              |
| `notebook_parent_ambiguous`   | error    | Multiple parent declarations/targets or ambiguous link resolution                     |
| `notebook_parent_kind`        | error    | Parent is not an area, project, or notebook; chain cannot reach an owner              |
| `notebook_cycle`              | error    | Self-parent or a cyclic parent chain                                                  |
| `notebook_checkbox`           | error    | Any checkbox list row outside fenced code, at any depth, regardless of status or tags |
| `notebook_child_kind`         | error    | Area, project, ref, or record instance names a notebook as its parent                 |
| `notebook_duplicate_block_id` | error    | A block ID is repeated within the notebook outside fenced examples                    |
| `notebook_not_at_root`        | error    | Notebook is below a subdirectory rather than at the vault root                        |
| `notebook_summary_missing`    | warning  | Summary absent or blank                                                               |
| `notebook_summary_long`       | warning  | Summary exceeds 140 characters, measured as characters rather than bytes              |
| `notebook_summary_multiline`  | warning  | Summary has multiple lines                                                            |
| `notebook_shape`              | warning  | Content departs from the supported notebook shape                                     |
| `notebook_parent_unquoted`    | warning  | Parent uses the unquoted `[[x]]` spelling                                             |

Use existing Markdown helpers where they match this contract. Checkbox matching must
cover unordered `-`, `*`, and `+` list rows and ordered rows, arbitrary status
characters, and nested rows, without requiring `#task`. Handle backtick and tilde
fences, including nested bullet content, and preserve physical line numbers. Body
examples in fenced code are inert.

The soft shape is at most one early H1, one optional preamble paragraph, column-zero
note bullets, and H2 sections. Warn for numbered top-level lists, `====` dividers, H3+,
extra/misplaced H1s, and stray top-level paragraphs. Nested detail under a note may
contain free-form text, links, images, code, and lists; do not report these as stray
paragraphs or flatten them. A nested checkbox still violates the hard no-checkbox rule.
Findings never rewrite a file.

## 3. List, check, output, and command discovery

Add the `notebooks` noun to the Vault section of root help. Its membership is commands
that inspect or maintain notebook notes; this phase supplies only `check` and `list`,
alphabetically, with bare `bob notebooks` defaulting to list.

```text
bob notebooks [list] [-b DIR] [-f human|json] [-r ROOT]
bob notebooks check [-b DIR] [-f human|json]
```

Use `--bob-dir/-b`, `--format/-f`, and `--root/-r`; all public long options have short
aliases and help options stay alphabetical. Root filtering uses the computed root
identity, never notebook ownership or directory location. Document and test the same
behavior for bare and explicit list invocations. A filter with no matches yields a valid
empty report. Findings do not make list nonzero; check exits 1 if it finds errors, 0 for
warning-only/clean reports, and 2 on usage errors. Real I/O failures must be reported,
never converted into a misleading clean scan.

List JSON has `ok`, `schema_version: 1`, `notebooks`, `catalogs: []`, and
`counts: {notebooks, roots, errors, warnings}`. Each notebook includes `stem`, `path`,
`title`, `summary`, `parent`, `parent_kind`, `owner`, `root`, `breadcrumb`, `children`,
`notes`, `sections: [{title, notes}]`, `last_note`, and `issues`. Missing ownership/date
values are null, and invalid notebooks are retained. Use one documented report shape for
list and check, with `ok` reflecting whether error findings exist; exit policy remains
command-specific. Counts match the reported set after list filtering. Every JSON
envelope includes `schema_version: 1` and emits no ANSI escapes or human preamble.

Human list output uses `style.rs`, the resolver's root hue, root headers, tree glyphs
for nested notebooks, dim summaries, issue indicators, and aligned `N notes · M § · age`
counts. Invalid/unowned notes get a visible group. Check groups actionable findings by
notebook and ends with a notebook/root/error/ warning summary. Respect NO_COLOR and
piped output; do not make the rendering depend on terminal width or mtimes in tests.

Wire `NativeCommand` variants and dispatch in `native.rs`, the group and help in
`runner.rs`, command catalog rows in `catalog/table.rs`, and CLI builders in
`completion/tree.rs`. Extend `completion/kinds.rs` and `providers.rs` with a provider
backed by the notebook scan for the root/stem selector, offering the available computed
roots for `-r`. Preserve command catalog coverage, root workflow-section contiguity,
alphabetical ordering, and option-kind coverage. This shell provider must not broaden
the task-route provider.

## 4. Teaching refusals without broadening destinations

Add explicit notebook handling to `parent_notes::check_non_candidate_note` and
`task_move::plan::classify_dest`. For a valid notebook, report:

```text
x.md is a notebook and holds no tasks — use its owner @dev
```

Resolve the owner through `HomeResolver`, including when the notebook is nested under
another notebook. Use the task-move snapshot for that path, including staged notes,
rather than loading the live vault behind its back. Refactor the classifier's context or
enrich the destination error at its callers as needed; both destination listing and the
actual move must retain their existing eligibility rules. If no owner resolves, teach
that notebooks hold no tasks and direct the user to choose an area/project and repair
the notebook with `bob notebooks check`; never invent `@unfiled` as a usable route.

Use the same refusal wording for parent resolution consumed by references, Highlights,
Gmail and other integrations. Check the shared resolver tests and representative caller
coverage. Notebook candidates must remain absent from task-move destinations,
inbox-routing destinations, parent candidates, and `scan_capture_targets`.
