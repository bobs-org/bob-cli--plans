# Fix the `:` Task Link Picker deadlock and close epic bob-cli-2v

## Context (verified while planning)

### The bug in Bryan's note on bob-cli-2v

Bryan installed bob-cli `f7d9c58` and bob-mac-capture `e9865e6` on the `mac` host and
typed `:`. The panel showed the calm status "Pick any open task — press Tab to browse",
but the picker card never opened.

**Root cause: a stdout pipe deadlock in `Sources/CaptureCore/BobProcessClient.swift`,
`run(arguments:environmentOverrides:lane:cancelsPreviousInLane:timeout:)`.**

- `run` attaches `Pipe()`s to stdout and stderr, but reads them
  (`readDataToEndOfFile()`) only inside `process.terminationHandler`, after the child
  has exited.
- A pipe holds at most 64 KiB. A child that writes more blocks in `write(2)` and never
  exits. The termination handler never fires, so the call hangs until the 20 s
  `defaultTimeout` kills it and throws `BobClientError.timedOut`.
- `capture-complete --all-tasks --cursor 1 -- ':'` on Bryan's real vault returns **592
  candidates, 246,378 bytes of JSON**. Every other completion context returns a few KiB,
  which is why the `^` picker and everything else work.
- CI missed it because every `task_link` fixture has at most 8 rows, so only a few KiB.

**Evidence gathered on the `mac` host with the real `~/.cargo/bin/bob` and `~/bob`
vault:**

- A standalone Swift repro using the same pattern (read in `terminationHandler`) was
  still running after 8 s for `:`. A 74-byte response returned in 14 ms.
- A harness compiled from the unmodified `Sources/CaptureCore/*.swift` failed
  `captureComplete(":", cursor: 1)` after 21.3 s with
  `bob command timed out after 20s and was terminated`.
- The same harness with a prototype concurrent-drain patch returned `context=task_link`,
  592 candidates, in 0.068 s.
  - `TaskLinkPickerIndex(candidates:)` built in 0.048 s: 55 grouped sections.
  - Filters `:b`, `:bob`, `:gtd proc`, and a no-match query each presented in 6–14 ms.
  - `:gtd` at the caret returned 166 `task_link` rows.

  So after the fix, decoding, grouping, and ranking all behave on vault-sized data.

- bob-cli is correct and needs no code change:
  - `capture-parse ':'` reports `needs: ["task_link"]`.
  - `capture-complete` answers `task_link` for `:`, for `:gtd`, and for the second item
    of `Buy milk\n\n:` (replacement `{10,11}`, 592 rows).

### A second, smaller defect in the same flow

`CapturePanelModel.openPickerFromChip()` (Tab or click on the reopen chip) refetches at
`r.start` whenever `chip.cursor != r.start`.

- For `.taskLink`, Bob's replacement includes the `:`, so the caret is always at least
  `r.start + 1`.
- As a result, every chip open on a bare `:` runs a redundant, now 246 KB,
  `capture-complete`, even though the chip already holds the full list.
- The landing tale fixed exactly this in `handleTaskLinkCompletion`
  (`cursor > r.start + 1`) but missed the chip path.

### 2. Fix the pipe deadlock in `BobProcessClient.run`

In `Sources/CaptureCore/BobProcessClient.swift`, drain stdout and stderr **concurrently
while the child runs**. Never read them only after exit.

**Required semantics:**

1. **Start draining right after a successful `Self.launch(process)`.** Read each pipe to
   EOF on its own background reader: for example, two
   `DispatchQueue.global(qos: .userInitiated)` blocks calling `readDataToEndOfFile()`,
   tracked by a `DispatchGroup`.
   - Enter the group before launching, so an instant exit cannot race ahead of the
     readers.
   - If launch throws, balance the group and keep today's error path.
2. **Resume the continuation with a `BobProcessResult` only after all three are done:**
   - the process has terminated;
   - stdout has reached EOF;
   - stderr has reached EOF.

   The existing timeout must cover this whole span. Cancel `timeoutWorkItem` only when
   all three are done, not merely when the termination handler fires. A grandchild that
   holds a pipe open then times out cleanly instead of hanging forever, as it would
   today.

3. **Keep these behaviors byte-for-byte:**
   - the `ResumeGuard` single-resume guarantee;
   - `terminateIfRunning` on timeout, lane replacement, and task cancellation;
   - `clearActiveProcess` / `clearActiveProcessAlreadyOnStateQueue`, including the
     no-reentrant-`stateQueue.sync` rule already documented there;
   - the `pthread_sigmask` launch wrapper;
   - UTF-8 decoding of both streams;
   - every `BobClientError` case and message.
4. **Keep the new helper small and private to the file**, for example
   `private final class ProcessOutputDrain: @unchecked Sendable`.
   - Guard its buffers so reads only happen after the group completes.
   - Add a brief comment explaining why draining must be concurrent: the 64 KiB pipe
     buffer, and `task_link` responses of hundreds of KiB.
5. **CaptureCore must still build on Linux** (the `Glibc` path). Use only Foundation and
   Dispatch.

### 3. Regression tests for the deadlock (the tests that would have caught Bryan's bug)

dispatch:

- `FAKE_BOB_BULK_STDERR_BYTES=<n>`: write `n` bytes to stderr **first**, for example
  `head -c "$n" /dev/zero | tr '\0' 'e' >&2`.
