# Drop the `<!-- bob:task-status-badges:v1 -->` marker: the badge row identifies itself

## Problem

`bob task reconcile` (and `bob task reroll`, which shares the grouping transform) writes
a hidden ownership comment above every generated status-count badge row in area/project
`Tasks` sections:

```markdown
## Tasks

<!-- bob:task-status-badges:v1 -->

[`⚪ 1 open`](#Alpha#Tasks) · [`🔵 2 next/wip`](#Alpha#Tasks#Next%20&%20In%20Progress) ·
[`🔴 0 blocked`](#Alpha#Tasks#Blocked) ·
[`🟢 3 done/canceled`](#Alpha#Tasks#Done%20&%20Canceled)
```

The vault currently has 87 of these comments (one per decorated container). Bryan wants
them gone.

The marker exists so the grouping parser (`src/native/task_status_groups/parse.rs`) and
capture placement (`src/native/capture/sections.rs::tasks_heading_end_after_badges`) can
find "the generated row" and replace or skip it. The marker is not needed for that,
because the row has a strict, machine-generated grammar that hand-written prose never
matches. It is four fixed-order code-span chips (`⚪ N open`, `🔵 N next/wip`,
`🔴 N blocked`, `🟢 N done/canceled`), each optionally wrapped in a `(#...)` heading
link, joined by `·`. The row can be its own identifier.

The marker design is also slightly hazardous today. `badge_piece_end` makes the marker
own whatever non-blank line follows it, so a marker left behind after the row was
deleted would swallow the next line, even a task. Recognizing the row by its shape
removes that hazard.

No consumer outside bob-cli depends on the marker. `bob-plugins` has no reference to
`bob:task-status-badges`, and Bob Mac Capture is a thin client of `bob`.

## Design

### 1. Badge-row recognizer (new, `task_status_groups`)

Add a pure function, `pub(crate) fn is_badge_row(line: &str) -> bool`, in
`src/native/task_status_groups/parse.rs` and re-export it as needed so `capture` can
call it. Ignoring trailing whitespace and any `\r`, a line is a badge row iff:

- it splits on the exact separator `" \u{b7} "` into exactly 4 chips;
- chip _i_ has the label pair (⚪, `open`), (🔵, `next/wip`), (🔴, `blocked`), or (🟢,
  `done/canceled`), in that order;
- each chip is either an unlinked code span `` `{emoji} {digits} {label}` `` or a linked
  one ``[`{emoji} {digits} {label}`]({anchor})``, where `{digits}` is one or more ASCII
  digits and `{anchor}` is non-empty, starts with `#`, and contains no whitespace and no
  `)`. Each chip may be linked or unlinked independently. Counts and anchors are not
  validated against the document, because they are regenerated anyway.

Keep the grammar's labels and emojis in one place shared with `render_badges` in
`emit.rs`, for example a `const BADGE_CHIPS: [(&str, &str); 4]` table that both the
renderer and the recognizer iterate. The two cannot then drift apart.

Add a second small predicate,
`pub(crate) fn is_legacy_badge_marker(line: &str) -> bool`. It is true for any
standalone HTML comment whose inner text starts with `bob:task-status-badges:`, using
the existing `markdown::standalone_html_comment` helper. It exists only to migrate old
notes.

### 2. Grouping parser (`parse.rs`, `mod.rs`)

- Delete `BADGE_MARKER`, `BADGE_MARKER_PREFIX`, `parse_badge_marker`, `badge_piece_end`,
  and `badge_marker_audit`.
- In `parse_direct_pieces`, replace the marker branch. With `allow_badges` (container
  intake), a line that is a badge row **or** a legacy marker becomes a one-line
  `DirectPiece::Badges { byte_range }` piece, after `flush_other` as today. A legacy
  marker never claims the following line. If that line is a badge row, the next loop
  iteration recognizes it on its own; otherwise it stays as ordinary content. The
  planner already drops every `Badges` piece and `render_badges` emits one fresh row in
  the slot, so the following all fall out of the existing flow without new code:
  duplicate rows, rows that drifted below a capture, and leftover legacy markers. They
  self-heal instead of failing closed. The duplicate case is safe now because each
  dropped line is proven generated by its grammar. The old marker could own arbitrary
  content, which is why duplicates used to fail closed.
- Without `allow_badges` (managed group bodies and `adoptable_group_body`), a badge row
  or legacy marker keeps failing closed. Rename the skip code
  `GroupingSkipCode::MalformedBadgeMarker` / `"malformed_badge_marker"` to
  `MisplacedBadgeRow` / `"misplaced_badge_row"` with the message
  `"status badge row inside a managed status group in {title:?} at line {line}"`.
  Replace `badge_marker_in_span` with an equivalent `badge_row_in_span` that matches
  either predicate. `classify_children` keeps using it on group-heading bodies, so the
  specific code still wins over `OwnershipCollision`.
- In `classify_children`, drop the `badge_marker_audit` call. Its remaining jobs
  (version check, duplicate check, "outside the first exclusive span") are now handled
  by self-heal, or cannot happen because a container has only one exclusive span before
  its first child heading.
- `ParsedContainer::has_badges` keeps its meaning ("the intake contains generated badge
  lines"). An orphaned row or a bare legacy marker in a container with no groupable
  tasks and no groups is therefore still removed. This is also how legacy markers in
  undecorated containers get cleaned up.

### 3. Emitter (`emit.rs`)

`render_badges` returns `format!("{row}{newline}{newline}")` with no marker line. Leave
everything else (chip order, anchor encoding, the unlinked fallback when an ancestry
segment contains `#`, the blank line before the intake) unchanged.

### 4. Capture placement (`src/native/capture/sections.rs`)

Rewrite `tasks_heading_end_after_badges` (rename it to
`tasks_heading_end_after_badge_row` if you like) to start at `heading_index + 1`:

1. If that line is a legacy marker, advance `heading_end` past it and move to the next
   line.
2. If the current line is a badge row (`task_status_groups::is_badge_row`), advance
   `heading_end` past it.

Unlike today, an unrecognized non-blank line after a legacy marker is **not** skipped.
Capture still inserts empty-section tasks below the row for both migrated and unmigrated
notes.

### 5. Migration of the 87 existing comments

No separate migration command is needed. `bob task reconcile` already rewrites every
grouping-eligible area/project note whose layout changes. With the new emitter, every
decorated container's output differs from its input by exactly the dropped marker line,
so the first post-upgrade run strips all of them idempotently. Undecorated containers
holding a stray legacy marker hit the orphan-removal path. `bob task reroll` uses the
same transform and migrates any note it touches. Keep the legacy-marker predicate
permanently. It is a few lines and keeps old backups and unsynced machines clean.

Do **not** run a live `bob task reconcile` against `~/bob` as part of this work. That
write belongs to Bryan's normal reconcile flow. Do run the read-only check in
Verification.

## New and rewritten tests

In `task_status_groups/tests.rs`:

1. `is_badge_row` accepts the linked row, the all-unlinked row, and a mixed row. It
   rejects wrong chip order, a wrong label, a missing chip, a fifth chip, a non-digit
   count, an anchor with a space or `)`, a `- ` list prefix, and leading prose.
2. **Marker-free output:** a grouped fixture emits the row directly under `## Tasks`
   with no `task-status-badges` text, and a re-run is byte-identical
   (`assert_idempotent`).
3. **Legacy migration:** input with `<!-- bob:task-status-badges:v1 -->` plus a stale
   row produces output with no marker and one fresh row in the slot, and is idempotent.
   Repeat the case with CRLF line endings.
4. **Legacy marker never eats content:** a legacy marker directly followed by a
   non-badge prose line (for example `Project context.`) drops the marker but keeps the
   prose line.
5. **Duplicates self-heal:** two badge rows in the intake, one under the heading and one
   below the intake prose, produce exactly one row, in the slot, with no warning.
6. **Misplaced row fails closed:** a badge row inside a managed group body leaves the
   container's bytes unchanged and reports `MisplacedBadgeRow`. The same applies to a
   legacy marker in a group body.
7. **Orphan removal:** a badge row with only Ready tasks and no groups is removed. A
   bare legacy marker in an undecorated container is also removed.
8. **Prose look-alike is preserved:** a line that only resembles the row (for example
   ``Counts: `⚪ 1 open` ``) in a decorated container's intake survives a rewrite as
   ordinary intake prose.

In `capture/tests/placement.rs`, cover empty-section insertion below a marker-free row,
below a legacy marker plus row, and below a legacy marker followed by prose. In the last
case the task goes after the marker only, not after the prose.

## Verification

1. `just fmt`, `just lint`, `just test` (or `just all`) pass.
2. `rg -n "task-status-badges" src tests docs README.md` matches only the legacy-marker
   predicate and its migration tests/docs sentence.
3. Read-only check against the live vault with the freshly built binary:
   `cargo run --quiet -- task reconcile --dry-run --format json --bob-dir ~/bob`.
   Confirm that it reports no `misplaced_badge_row` or other new grouping warnings, and
   that the grouped sections it lists are the marker-bearing notes. A second dry run
   cannot show convergence without a write, so idempotence is covered by the unit tests
   rather than by the vault.

## Out of scope

- The separate `<!-- bob:task-status-group:v1:{active,blocked,closed} -->` comments
  under the generated `Next & In Progress` / `Blocked` / `Done & Canceled` headings
  stay. They carry real ownership information: they let bob keep owning a group heading
  after Bryan adds prose inside it, while an unmarked same-named heading with authored
  content is treated as Bryan's (`OwnershipCollision`). Removing them would need its own
  design.
- No change to chip order, labels, counts, anchors, or when containers are decorated.
